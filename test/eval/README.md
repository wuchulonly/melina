# 本地场景题库

主清单只收目标明确、但需要通过观测与实验才能摸清中间状态的问题。解题过程可以写临时脚本；交付对象是调查结论、数据、配置或操作步骤。实现函数、修改项目代码、让隐藏单元测试通过的编程题已移出。

现有内置题是开发集：18 道业务逻辑的受控仿真，2 道离线调查。它们不是生产系统或留出集，成绩只能作为开发集成绩。可选 Web/API 审计由外部的 `melina-lab-infra/benchmarks/tasks.ts` 维护。

## 当前清单

| 场景 | 任务 id | 需要调查的未知项 | 交付 |
| --- | --- | --- | --- |
| 旧订单 API 的完整对账 | `service-medium`、`service-hard`、`service-extreme`、`service-quota` | 接口实际行为、数据完整性、精度及访问限制 | 经过核对的订单数与金额 |
| 现有部署平台的约束探测 | `constraints-medium`、`constraints-hard`、`constraints-extreme` | 文档没有覆盖的平台约束及其组合 | 可通过校验的部署清单 |

共 20 道：中等 3 道，难 17 道。`test/eval/tasks.ts` 的 `scenarios` 是主清单的显式白名单。新增题需要检查场景与未知项后再加入。

新增九道的探索方式类似 CTF：从明确的业务结果出发，观察接口、提出假设、用成功和失败请求排除解释，再复现完整状态链。成功条件围绕同一测试工作区的数据一致性与正常业务操作。每题交付 `answer.json`、记录实际请求及完整响应的 `evidence.json` 和引用成功、失败观测的 `report.md`；判题从干净初态重放证据，再核对结果与指定对照。隐藏规则与标准解只留在判题端。

## 选题与检查

`all` 和 `scenarios` 都是这 20 道；可以按 `service`、`constraints`、`tuning`、`research`、`web`、`workflow`，或用 `scenarios:medium`、`scenarios:hard` 筛选。`business` 只选新增九道。不指定 `--tasks` 时跑 3 道中等场景，外部 `--tasks-file` 仍默认跑该文件里的 `all`。

下面的命令只跑题库自带的标准解和直接做法，不调用模型：

```sh
node test/eval/score.ts --contender reference --contender naive --tasks scenarios --n 1
```

验题要求：标准解通过，空交付不通过，照文档直接做或未经调查的猜测不通过。判题在 Run 外完成，真值与参考解不作为给 agent 的材料。

`test/sim/` 的完整仿真清单继续供机制回归使用，其中的按键状态机和三个简单档不进入主评测。历史报告保留原有题目、任务集与成绩口径；旧命令中的 `code`、已移出题目 id、`gate1` 和 `harness:easy` 在主题库中会明确报错。

## 新题标准

- 起点给业务目标、允许的操作范围、入口和必要的账号或样本；隐藏的机制与正确答案留在判题端。
- 至少存在需要调查的行为、状态、规则或因果关系；单靠已完整给定的计算口径不能完成。
- 可通过接口请求、材料检查、受控实验等动作验证假设，并允许失败的探索路线。
- 交付需要可核对的结果和复现证据，不要求修改项目代码或提交软件实现。
- 保留可执行判题、参考解和无法达标的直接做法，确保题目可解且确实需要调查。
